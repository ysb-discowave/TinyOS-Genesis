状态横幅：✅ pkg 已实现（v0.1）

✅ v0.1 已实现 pkg 命令（用户态）

pkg 是用户态 TNCR 程序的一部分，实现在 tools/tinysh/src/tinysh.c（随 tinysh 一起编译成 tinysh.TNCR），不是内核内建 —— 它需要 shell、配置解析和大量文件读写，这些都不该放进内核。内核只暴露 sha256_file 这一个原语。提供 7 个子命令：help / list / info / verify / install / remove / source。安装源有三种，按顺序回退：① 本地源目录（sourcedir）② FTP ③ HTTP 镜像。SHA256 校验对下载与本地包同样生效。

联网下载已跑通：默认 HTTP 源是一个 Cloudflare Worker（tinyos-pkg-down.ysbdwz.dpdns.org:80），它在边缘终结 TLS、再用 HTTPS 回源拉 GitHub 上的包，然后以明文 HTTP 喂给 TinyOS。所以内核不需要 TLS 栈也能真正联网装包 —— 加密由边缘承担，内核只说 HTTP。详见下方「联网下载」与「.pack 多文件包」两节。

快速上手：装一个包（3 步）✅

pkg install 会依次尝试三个源：① 本地源目录（sourcedir）② FTP ③ HTTP 镜像。所以「本地装」和「联网装」用的是同一条命令 —— 放本地就离线用，不放就自动走网络。下面以把内置的 packages/repo/ 模板作为本地源为例：把源目录放到 /home/pkgrepo，确认 /etc/pkg.conf 里的 sourcedir，然后 pkg install。

  1. 1. 放源目录 /home/pkgrepo 含 *.tncr + *.manifest
  2. →
  3. 2. 确认配置 /etc/pkg.conf: sourcedir
  4. →
  5. 3. pkg install 校验通过 → /bin/<name>.TNCR

入口命令

# 1) 把 packages/repo/ 放到 TinyOS 的本地源目录（默认 /home/pkgrepo）
#    该目录需含 <name>.tncr（产物）+ <name>.manifest（描述）

# 2) 确认 /etc/pkg.conf 里的 sourcedir 指向它
#    pkg.conf.example 内容：  sourcedir /home/pkgrepo

# 3) 安装
pkg install tinysh

源目录不存在时会明确报错

若 /home/pkgrepo 还没准备好，pkg install 不会静默失败，而是打印 pkg: source dir missing: /home/pkgrepo，提示你先把源目录放到位。

联网下载：Worker 中转，内核只说明文 HTTP ✅

GitHub 已全面强制 HTTPS：明文请求 raw.githubusercontent.com 只会拿到 301 跳转、没有任何内容。而 TinyOS 内核刻意不做 TLS（只有 SHA-256，没有 AES/GCM/X25519，也没有 X.509 与主机名校验）。解法不是在内核里硬塞一套密码学，而是把 TLS 交给边缘 —— 这就是 Cloudflare Worker 中转。

  1. 1. TinyOS 明文 HTTP GET /tinysh.tncr
  2. →
  3. 2. Cloudflare 边缘 TLS 在这里终结
  4. →
  5. 3. GitHub Worker 用 HTTPS 回源 
# 默认配置（/etc/pkg.conf）已经指向 Worker 镜像
repo_host=tinyos-pkg-down.ysbdwz.dpdns.org
repo_port=80
repo_path=

# 于是联网装包就是同一条命令 —— 本地没有就自动走网络
pkg install tinysh

# 换个源（FTP 也能配）
# ftp_host=10.0.2.2
# ftp_port=21
# ftp_path=/packages/repo

为什么不用「跳过证书校验」的伪 TLS

pkg 下载完就要执行代码。如果为了「能连通」而不校验证书链和主机名，等于把中间人攻击的门直接打开 —— 那比明文更危险，因为它还披着 HTTPS 的外衣。所以内核宁可返回一个明确的 notls，也不提供假加密；真正需要加密的那一段，交给能正确校验证书的边缘去做。

多文件软件包：.pack 归档 ✅

单文件 .tncr 只够装一个程序。真实的大型软件往往要带一堆附属文件（工具、库、配置）。.pack 就是为此设计的：把一个目录打包成一个归档，安装时按元数据释放到指定目录，并顺手登记好程序映射与环境变量。

怎么做一个 .pack

# 1) 把要打包的文件放进一个目录（可含一层子目录）
mkdir /home/myapp
cp myapp.TNCR /home/myapp/
mkdir /home/myapp/bin
cp helper.TNCR /home/myapp/bin/

# 2) 打包（tinysh 内置命令，不用开 TinyOS 以外的东西）
pack /home/myapp -o myapp.pack --name myapp --dir /opt/myapp \
     --prog myapp=/opt/myapp/myapp.TNCR \
     --env PATH=/opt/myapp/bin

# 3) 把 myapp.pack 放进源目录后安装
pkg install myapp.pack

# 4) 直接按名字调用
run myapp --help

安装器会做什么

  • 按 install_dir 释放文件

    归档里 bin/helper.TNCR 这类带子目录的条目会自动建目录后落盘，最终得到 /opt/myapp/bin/helper.TNCR。

  • 写 /bin/path 注册表

    元数据里的 prog.* 与 env.* 会被写进 /bin/path，run 命令就是查这张表来定位程序的。

  • 为什么 .pack 不压缩

    用户态没有 inflate —— 内核的解压实现只服务 romfs，pkg 运行在用户态，拿不到它。所以 .pack 存的是原始字节。这是个诚实的取舍：换来的是「任何机器上解出来的结果完全一致」，代价是包体更大。

/bin/path 与 run

# /bin/path 就是一个纯文本键值表，两类键：
prog.myapp=/opt/myapp/myapp.TNCR     # 程序名 -> TNCR 路径
env.PATH=/opt/myapp/bin              # 环境变量

# run 查这张表再执行，等价于「按名字跑程序」
run myapp --help

为什么 VERSION 显示 ?、[tT]NCR 是什么

pkg list 里 VERSION 显示 ?，是因为这些包是随镜像内置的、未经 pkg 登记（info 里也写作 unregistered: only raw /bin file present）。报错里的 [tT]NCR 是“兼容大小写扩展名”的写法：源文件既可以是 .tncr 也可以是 .TNCR。这两点都如实说明，不影响功能。

SHA256 校验：供应链安全的底座 ✅

pkg 的 install 与 verify 都做 SHA256 比对，确保装进系统的二进制跟源里登记的一致。这是真实的实现，不是占位。

为什么重要

软件包从源到 /bin 之间若被改动（传输截断、源被替换、磁盘损坏），肉眼看不出来。SHA256 在落盘前先算一遍、跟 manifest 登记值比对，从源头拦截“装了个不一样的包”。这是供应链安全的基本盘。

它是真怎么工作的

复用内核 src/kernel/sha256.c 里的 sha256_init / sha256_update / sha256_final / sha256_hex。

  • install 时

    读 manifest 的 sha256 字段，对源二进制算实际值比对；不符则报 pkg: sha256 mismatch: <name>，绝不写入。

  • verify 时

    同样比对 /etc/packages.d/<name> 里登记的值，输出 OK 或 MISMATCH。

实测的 tinysh 校验值

sha256: 4c317df355a489aeea5d6f26447f0a0472c67afc7c83b2f4fa4c8229f567f2bc
size  : 179104 bytes  (file: tinysh.TNCR)

这个值是 QEMU 实测算出的真实哈希，已回填进 packages/tinysh/tinysh.manifest 的 sha256 字段。因此对 tinysh 而言，install 与 verify 都能做真正的完整性校验。

本地源目录：结构、配置与模板 ✅

install 从一个可配置的本地目录读取，默认 /home/pkgrepo，可在 /etc/pkg.conf 的 sourcedir 里改。源目录里要放：<name>.tncr（产物）+ <name>.manifest（描述）。校验通过后写入 /bin/<name>.TNCR 并登记到 /etc/packages.d/<name>。

源目录结构

<sourcedir>/
├─ <name>.tncr        # 产物（二进制，扩展名大小写均可）
└─ <name>.manifest    # 包描述：含 sha256 等字段

# 例：/home/pkgrepo/tinysh.tncr + /home/pkgrepo/tinysh.manifest

/etc/pkg.conf 配置

# /etc/pkg.conf
sourcedir /home/pkgrepo

v0.1 内置包仍走 romfs 路线 ✅

pkg 只能装“你放进源目录的包”。系统随镜像自带的那一批（lua、tinysh、sshd、CC、EDIT、JVM 等）其实来自只读文件系统 romfs，与 pkg 无关 —— 它们已经作为 .TNCR 躺在 /bin 下，内核挂载后直接可执行。

  1. tools/build_users.py 交叉编译用户程序 → .TNCR
  2. →
  3. tools/mkromfs.py 打包压缩进 romfs
  4. →
  5. kernel boot 挂载 romfs 到 VFS
  6. →
  7. /bin/*.TNCR 直接可执行

一条命令就能用，靠的是 romfs 不是 pkg

lua、tinysh、sshd、CC、EDIT 等之所以“装好即用”，是因为它们已经作为 .TNCR 在 romfs 的 /bin 下，内核挂载后直接可执行。这与 pkg 命令无关 —— pkg 是用来叠加安装你自己的本地包的。

边界与未实现 🚧

诚实区：下面这些在 v0.1 里仍是未实现。不要把它们当成已可用功能。

🚧 内核仍无 TLS：CONNECT 隧道可用，密文读不了

内核有最小 HTTP/1.1 客户端（src/kernel/net/http.c）与 HTTP CONNECT 代理支持，隧道能建起来，但隧道之后需要 TLS 栈才能读密文 —— 这一步内核做不到，所以会明确返回 notls。默认路径不依赖它：pkg 走 Cloudflare Worker 中转，TLS 在边缘终结，内核对上游只说明文 HTTP。

为什么不用「跳过证书校验」的伪 TLS：内核只有 SHA-256，没有 AES / GCM / ChaCha20 / X25519，也没有 X.509 解析与主机名校验。一套能用的 TLS 1.3 客户端约需 1500 行以上裸机密码学代码，而且必须校验证书链到内置根 CA 并核对主机名。pkg 用来下载并执行代码，跳过证书验证等于给中间人开门 —— 那比明文更危险。所以内核宁可返回明确的 notls，也不提供「假装加密」的伪 TLS。

  • 🚧 依赖解析未实现

    manifest 里 dependencies 字段已经定义，但 pkg 不会自动拉取或检查依赖。装上 A 时不会自动装它依赖的 B；依赖关系现在只是“被记录”，不被“被执行”。

  • 🚧 版本显示 ? 的原因

    随镜像内置的包未经 pkg 登记，pkg list / pkg info 拿不到版本，于是显示 ?，info 注为 unregistered: only raw /bin file present。这是数据缺失，不是 bug。

  • 🚧 .pack 目录只支持一层子目录

    pack 命令目前把源目录及其下一层子目录收进归档，更深的嵌套会被跳过。已实测可用（20/20 端到端用例通过），但递归深度是已知限制。另外 .pack 不压缩，原因见上一节。
